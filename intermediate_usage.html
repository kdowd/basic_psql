A real table, with real problems in it

Sixteen games, eight columns, five data types — and three things wrong with the data, on purpose. Over the next hour you will build it, interrogate it, and then safely fix it.

This assumes you can already open psql, create a database, and read a SELECT. If not, basic_usage.html gets you there in six steps. Everything below was run against PostgreSQL 18.6 on this machine, so the output under each query is the output you should get.

1. The shape of the thing

A catalogue of games you own. Eight columns, and the type of each one is a decision you are making about your own data:

Column Type Why
id integer, identity The database hands out 1, 2, 3… on its own. You never type it, and it is the primary key: unique, never null, and indexed.
title text Words. NOT NULL — a game with no title is not a game.
genre text Words again. You will group by this later.
price numeric(6,2) Money. numeric stores exact decimals — up to 6 digits, 2 after the point. Never store money in a float: 0.1 + 0.2 is not 0.3 in binary.
released date A calendar day, and it sorts and compares like one.
rating numeric(3,1) The only column with no NOT NULL: a new release may not be rated yet, and that is real information, not zero.
hours_played integer, default 0 Counts up. If you leave it out of an insert, Postgres writes 0 for you.
finished boolean, default false True or false, nothing in between. Defaults to false for the same reason.

The games are invented. Nothing here describes a real product, price or release date — which also means the data can be exactly as awkward as I want it to be.

2. Build it

Its own database, so nothing here can disturb your earlier work:

psql -U postgres
CREATE DATABASE gamevault;
\c gamevault
CREATE DATABASE
You are now connected to database "gamevault" as user "postgres".

If instead you get ERROR: database "gamevault" already exists, it has been created before. That is not a failure — skip the CREATE DATABASE line and go straight to \c gamevault. Re-running a script without it exploding is worth designing for, and the companion script is built that way: it drops the table and rebuilds it from scratch every time.

Now the table. Read it once before you type it — the constraints are the interesting part:

CREATE TABLE games (
    id           integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title        text    NOT NULL,
    genre        text    NOT NULL,
    price        numeric(6,2) NOT NULL,
    released     date    NOT NULL,
    rating       numeric(3,1),
    hours_played integer NOT NULL DEFAULT 0,
    finished     boolean NOT NULL DEFAULT false
);
CREATE TABLE

Ask Postgres what it actually built — this is your first reflex whenever a query misbehaves:

\d games
                               Table "public.games"
    Column    |     Type     | Collation | Nullable |           Default
--------------+--------------+-----------+----------+------------------------------
 id           | integer      |           | not null | generated always as identity
 title        | text         |           | not null |
 genre        | text         |           | not null |
 price        | numeric(6,2) |           | not null |
 released     | date         |           | not null |
 rating       | numeric(3,1) |           |          |
 hours_played | integer      |           | not null | 0
 finished     | boolean      |           | not null | false
Indexes:
    "games_pkey" PRIMARY KEY, btree (id)

Note the empty Nullable cell on rating — the only column allowed to be missing — and that the primary key arrived with an index attached, for free.

4. Ask it questions

What have I never played?

SELECT title, price FROM games WHERE hours_played = 0;
   title    | price
------------+-------
 Glasshouse | 27.50
(1 row)

What did I pay full whack for?

SELECT title, genre, price FROM games WHERE price >= 50 ORDER BY price DESC;
    title     |  genre  | price
--------------+---------+-------
 Redline Zero | Shooter | 69.99
 Hollow Keep  | RPG     | 59.99
(2 rows)

What is still unfinished?

SELECT title, released FROM games WHERE NOT finished ORDER BY released DESC;
     title     |  released
---------------+------------
 Redline Zero  | 2025-02-27
 Iron Verdict  | 2024-09-05
 Velvet Static | 2024-04-08
 Hollow Keep   | 2023-11-02
 Marrow        | 2023-08-11
 Dust & Diesel | 2022-07-15
 Static Bloom  | 2022-01-14
 Glasshouse    | 2021-11-19
(8 rows)

WHERE NOT finished works because finished is a boolean, so it is already a condition on its own. WHERE finished = false means exactly the same thing.

What is recent?

SELECT title, released FROM games WHERE released >= '2023-01-01' ORDER BY released DESC;
     title     |  released
---------------+------------
 Redline Zero  | 2025-02-27
 Iron Verdict  | 2024-09-05
 Velvet Static | 2024-04-08
 Hollow Keep   | 2023-11-02
 Marrow        | 2023-08-11
 Echo Vault    | 2023-05-09
(6 rows)

A date in single quotes is compared as a date, not as text. That is why '2023-01-01' works the way you expect — and why you should write dates as YYYY-MM-DD and never as 01/02/2023, which means two different days depending on which side of the Atlantic you are standing.

5. Summarise it

Aggregates collapse many rows into one. Three of them in a single query:

SELECT count(*) AS rows, count(rating) AS rated, count(DISTINCT genre) AS genres
FROM games;
 rows | rated | genres
------+-------+--------
   16 |    13 |      6
(1 row)

16 rows, but only 13 ratings. That gap is the whole lesson. count(*) counts rows; count(rating) counts rows where the rating exists. They are different questions, and mixing them up is the most common way to get a plausible, wrong number out of a database. 

SELECT round(avg(rating), 2) AS avg_rating,
       round(sum(price), 2) AS catalogue_value,
       max(released) AS newest
FROM games;
 avg_rating | catalogue_value |   newest
------------+-----------------+------------
       4.11 |          458.86 | 2025-02-27
(1 row)

That 4.11 is the average of 13 ratings, not 16. The three unrated games were skipped, not counted as zero.

Now the useful one — one summary row per genre, which is where a table this size starts earning its keep:

SELECT genre,
       count(*) AS games,
       round(avg(rating), 2) AS avg_rating,
       sum(hours_played) AS hours
FROM games
GROUP BY genre
ORDER BY hours DESC;
   genre    | games | avg_rating | hours
------------+-------+------------+-------
 RPG        |     3 |       4.43 |   285
 Sim        |     3 |       3.85 |   234
 Roguelike  |     2 |       4.55 |   117
 Shooter    |     3 |       3.85 |    67
 Puzzle     |     2 |       4.40 |    34
 Platformer |     3 |       3.73 |    23
(6 rows)

Sixteen rows in, six rows out. GROUP BY genre means "make one output row per genre", and every aggregate in the SELECT list is then computed inside each group rather than over the whole table.

Look hard at Puzzle: an average of 4.40 from just two games, one of which has no rating at all. Averages over tiny groups are how you talk yourself into bad decisions. Add count(rating) to that query whenever a group might be small: 

SELECT genre, count(*) AS games FROM games
GROUP BY genre HAVING count(*) > 2 ORDER BY games DESC, genre;
   genre    | games
------------+-------
 Platformer |     3
 RPG        |     3
 Shooter    |     3
 Sim        |     3
(4 rows)

HAVING filters groups, the way WHERE filters rows. You cannot write WHERE count(*) > 2: WHERE runs before the groups exist. That is the one rule worth memorising from this section.

6. Missing is not zero

Three games have no rating. Ask for them explicitly — note that rating = NULL would return nothing at all, because equality against "unknown" is never true:

SELECT title, COALESCE(rating::text, 'unrated') AS rating
FROM games WHERE rating IS NULL;
    title     | rating
--------------+---------
 Static Bloom | unrated
 Glasshouse   | unrated
 Marrow       | unrated
(3 rows)

COALESCE returns the first argument that is not null — here, the rating if there is one, otherwise the word unrated. The ::text is a cast: a column can only hold one type, and 4.5 and 'unrated' are not the same type, so the number is converted to text to let them share a column.

And here is what that same decision does to an average, depending on how you handle the gap:

SELECT round(avg(rating), 2) AS avg_ignoring_nulls,
       round(avg(COALESCE(rating, 0)), 2) AS avg_null_as_zero
FROM games;
 avg_ignoring_nulls | avg_null_as_zero
--------------------+------------------
               4.11 |             3.34
(1 row)

4.11 is the honest average of the ratings that exist. 3.34 is what you get if you decide that "not rated yet" means "rated zero" — a number that is not just different, but meaningless. Whenever you reach for COALESCE in an aggregate, ask which of these two questions you are actually asking.

7. Find the duplicate

SELECT title, genre, count(*) AS copies
FROM games
GROUP BY title, genre
HAVING count(*) > 1;
    title    |   genre    | copies
-------------+------------+--------
 Paper Skies | Platformer |      2
(1 row)

Group by the things that make two rows "the same game", then keep the groups with more than one row. The two rows are id 3 and id 12 — identical in every column except the id, which is exactly why the primary key did not stop this. A primary key guarantees every row is unique; it cannot know that two rows describe the same game. Only you know that, which is why real schemas grow unique constraints on things like title once someone gets burned.

8. Your turn

Three questions about the catalogue. Work them out before opening the answers — the expected numbers tell you whether you were right, which is the whole point of stating them.

Which genres rate above 4.0?

Expected: 3 rows, columns genre, avg_rating, best first.

Answer 
SELECT genre, round(avg(rating), 2) AS avg_rating
FROM games
GROUP BY genre
HAVING avg(rating) > 4.0
ORDER BY avg_rating DESC;
   genre   | avg_rating
-----------+------------
 Roguelike |       4.55
 RPG       |       4.43
 Puzzle    |       4.40
(3 rows)

The trap is putting the condition in a WHERE clause — it has to be HAVING, because it is a statement about a group. If your Puzzle row looks like a win, remember it is one rating out of two games.

What have I paid for and never played?

Expected: 1 row, and a total amount of 27.50.

Answer 
SELECT count(*) AS never_played, round(sum(price), 2) AS wasted
FROM games WHERE hours_played = 0;
 never_played | wasted
--------------+--------
            1 |  27.50
(1 row)

The filter and the aggregate go in the same query: WHERE narrows the rows first, then sum() adds up what is left. If your total is 458.86, you summed the whole catalogue — the filter is missing.

Which genres have more than 100 hours in them?

Expected: 3 rows, columns genre, hours, largest first.

Answer 
SELECT genre, sum(hours_played) AS hours
FROM games
GROUP BY genre
HAVING sum(hours_played) > 100
ORDER BY hours DESC;
   genre   | hours
-----------+-------
 RPG       |   285
 Sim       |   234
 Roguelike |   117
(3 rows)

Same shape as exercise 1 with a different aggregate. Once you can see that, you have stopped memorising queries and started recognising them.

9. Changing data without regret

Everything so far only read. Now you write — and the first thing to learn is how to take it back. Here is the classic beginner disaster, run on purpose: an UPDATE with a typo'd or forgotten WHERE. 

BEGIN;
UPDATE games SET price = price + 10;
SELECT count(*) AS over_60 FROM games WHERE price > 60;
ROLLBACK;
BEGIN
UPDATE 16
 over_60
---------
       2
(1 row)

ROLLBACK

I meant to bump one game's price. UPDATE 16 says I hit every row in the table. BEGIN put the whole thing inside a transaction, and ROLLBACK undid it as if it never happened — verified, because the count is back to 1: 

SELECT count(*) AS over_60_after_rollback FROM games WHERE price > 60;
 over_60_after_rollback
------------------------
                      1
(1 row)

The habit that will save you a job one day. Wrap any UPDATE or DELETE in BEGIN; … check the result … COMMIT; (keep it) or ROLLBACK; (throw it away). It costs you one extra line and buys back any mistake short of a dropped table. And read the command tag every time: UPDATE 16 when you expected UPDATE 1 is the database telling you that you are about to have a bad afternoon.

Now the same operation done properly. One row, named by its primary key, with RETURNING so you can see exactly what changed:

UPDATE games
SET finished = true, hours_played = hours_played + 6
WHERE id = 8
RETURNING id, title, hours_played, finished;
 id |    title     | hours_played | finished
----+--------------+--------------+----------
  8 | Redline Zero |           18 | t
(1 row)

UPDATE 1

UPDATE 1. That is the receipt you want. RETURNING shows the row after the change, so you do not have to run a SELECT to find out whether it worked — and hours_played = hours_played + 6 reads the old value and writes the new one in a single step, with no need to know what it was.

10. Delete the duplicate, carefully

You found it, so remove it — inside a transaction, checking the count before you commit:

BEGIN;
DELETE FROM games WHERE id = 12;
SELECT count(*) AS rows_inside_transaction FROM games;
COMMIT;
BEGIN
DELETE 1
 rows_inside_transaction
-------------------------
                      15
(1 row)

COMMIT

DELETE 1 — exactly one row, which is what "the second copy of Paper Skies" should be. I kept id 3 and removed id 12 because the lower id is the original import; in a real system the copy you keep is the one other tables point at, and you would check that before deleting, not after. COMMIT makes it permanent: 

SELECT count(*) AS final_rows FROM games;
 final_rows
------------
         15
(1 row)

11. Where you are now

  • You designed a table with eight columns, five types, a primary key, defaults and one deliberately nullable field.
  • You can filter rows, sort them, and summarise them per group — and you know why HAVING is not WHERE.
  • You know that count(*) and count(column) answer different questions, and that a missing value is not a zero.
  • You can find duplicate rows and delete one of them without losing sleep, because you used a transaction and read the row count.

The next rung is a second table and a JOIN: genres belong in their own table with a name and an id, and games.genre becomes games.genre_id pointing at it. That is the moment a database stops being a tidy spreadsheet and starts being worth the trouble — and it is exactly the thing a spreadsheet cannot do.
