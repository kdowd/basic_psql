Two tables instead of one

Eight people. Each one has a first name, a last name, and a job. Storing all of that in one table works — right up until you need to change the name of a job, and discover you have to change it in three places.

This page builds the one-table version first, shows you the three things that go wrong with it, then splits it into two tables joined by a foreign key. Everything below was run against PostgreSQL 18.6 on this machine, so the output under each command is what you should get. The names are real people; the job matches are not — treat the whole table as sample data.

1. All of it in one table

Start a database of its own, then write everything you know as one row per person:

psql -U postgres
CREATE DATABASE jobsdb;
\c jobsdb

If you get ERROR: database "jobsdb" already exists, you have made it before — skip that line and go straight to \c jobsdb. 

CREATE TABLE people_flat (
    id        integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    firstname text NOT NULL,
    lastname  text NOT NULL,
    job_title text NOT NULL
);
CREATE TABLE

The id is there so every row has something unique to point at. The other three columns are the three facts you actually care about. Now the eight people:

INSERT INTO people_flat (firstname, lastname, job_title) VALUES
    ('Dave',    'Smith',    'Electrician'),
    ('Tenzing', 'Norgay',   'Mountaineer'),
    ('Anne',    'Wilson',   'Electrician'),
    ('Ta',      'Mok',      'Gangster'),
    ('Viv',     'Richards', 'Plumber'),
    ('Jane',    'Campion',  'Electrician'),
    ('Shakib',  'Khan',     'Actor'),
    ('Ayub',    'Bachchu',  'Musician');
INSERT 0 8
SELECT id, firstname, lastname, job_title FROM people_flat ORDER BY id;
 id | firstname | lastname |  job_title
----+-----------+----------+-------------
  1 | Dave      | Smith    | Electrician
  2 | Tenzing   | Norgay   | Mountaineer
  3 | Anne      | Wilson   | Electrician
  4 | Ta        | Mok      | Gangster
  5 | Viv       | Richards | Plumber
  6 | Jane      | Campion  | Electrician
  7 | Shakib    | Khan     | Actor
  8 | Ayub      | Bachchu  | Musician
(8 rows)

That is a perfectly good table. Every row is complete, nothing is missing, and every question you would ask about these eight people is a one-line SELECT. This is what makes the next section worth reading: the table is correct, and it is still a bad idea.

2. What goes wrong later

The same fact, stored three times

Count how often each job title appears:

SELECT job_title, count(*) AS people FROM people_flat
GROUP BY job_title ORDER BY people DESC, job_title;
  job_title  | people
-------------+--------
 Electrician |      3
 Actor       |      1
 Gangster    |      1
 Mountaineer |      1
 Musician    |      1
 Plumber     |      1
(6 rows)

Eight rows, but only six facts about jobs. The word Electrician is written out three times, and nothing in the database links those three copies to each other. They are just three strings that happen to match.

Anomaly 1 — one change, many rows

You decide electricians should be called Electrical Technicians. That is one fact about one job, so it should be one change:

BEGIN;
UPDATE people_flat SET job_title = 'Electrical Technician'
WHERE job_title = 'Electrician';
SELECT count(*) AS rows_changed FROM people_flat
WHERE job_title = 'Electrical Technician';
ROLLBACK;
BEGIN
UPDATE 3
 rows_changed
--------------
            3
(1 row)

ROLLBACK

UPDATE 3. One fact, three rows. Get it wrong — a typo in the WHERE, a row you forgot — and your table now disagrees with itself about what these people do. That is an update anomaly.

Anomaly 2 — deleting a person destroys a fact

Ayub leaves the music business entirely, so you delete him:

SELECT count(DISTINCT job_title) AS jobs_before FROM people_flat;
BEGIN;
DELETE FROM people_flat WHERE lastname = 'Bachchu';
SELECT count(DISTINCT job_title) AS jobs_after FROM people_flat;
ROLLBACK;
 jobs_before
-------------
           6
(1 row)

BEGIN
DELETE 1
 jobs_after
------------
          5
(1 row)

ROLLBACK

The number of job titles fell from 6 to 5. You deleted a person, and the fact that Musician is a job disappeared with him. Now the database cannot answer "what jobs exist?" without also assuming somebody currently does them. That is a delete anomaly.

Anomaly 3 — a fact that cannot exist on its own

You want to record that Blacksmith is one of the jobs on your list. There is no person doing it yet, so try adding the job on its own:

INSERT INTO people_flat (firstname, lastname, job_title)
VALUES (NULL, NULL, 'Blacksmith');
ERROR:  null value in column "firstname" of relation "people_flat" violates not-null constraint
DETAIL:  Failing row contains (9, null, null, Blacksmith).

Refused — and the only way to make it work would be to invent a person, or drop the NOT NULL constraints and allow a row that describes nobody. A table keyed on people simply has nowhere to put a fact about a job. That is an insert anomaly.

Three symptoms, one cause. The table is keyed on people, but a job title is not a fact about a person — it is a fact about a job, and it is being stored in the only place available. Fix the cause and all three symptoms disappear at once.

3. Split it in two

Give job titles their own table, and let each person point at one.

The jobs table

CREATE TABLE jobs (
    id    integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL UNIQUE
);

INSERT INTO jobs (title) VALUES
    ('Electrician'), ('Mountaineer'), ('Gangster'),
    ('Plumber'), ('Actor'), ('Musician');
CREATE TABLE
INSERT 0 6

Six rows, not eight — Electrician is in there once. The UNIQUE is doing real work: it tells Postgres that a second row called Electrician is a mistake, not a coincidence.

The people table

CREATE TABLE people (
    id        integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    firstname text    NOT NULL,
    lastname  text    NOT NULL,
    job_id    integer NOT NULL REFERENCES jobs(id)
);

INSERT INTO people (firstname, lastname, job_id) VALUES
    ('Dave',    'Smith',    1),
    ('Tenzing', 'Norgay',   2),
    ('Anne',    'Wilson',   1),
    ('Ta',      'Mok',      3),
    ('Viv',     'Richards', 4),
    ('Jane',    'Campion',  1),
    ('Shakib',  'Khan',     5),
    ('Ayub',    'Bachchu',  6);
CREATE TABLE
INSERT 0 8

The job title is gone from this table. In its place is job_id — a number pointing at a row in jobs. REFERENCES jobs(id) is the foreign key: it is a promise Postgres will enforce, that this number always names a job that exists.

Ask Postgres what it built:

\d people
                           Table "public.people"
  Column   |  Type   | Collation | Nullable |           Default
-----------+---------+-----------+----------+------------------------------
 id        | integer |           | not null | generated always as identity
 firstname | text    |           | not null |
 lastname  | text    |           | not null |
 job_id    | integer |           | not null |
Indexes:
    "people_pkey" PRIMARY KEY, btree (id)
Foreign-key constraints:
    "people_job_id_fkey" FOREIGN KEY (job_id) REFERENCES jobs(id)

Two tables, side by side:

SELECT * FROM jobs ORDER BY id;
 id |    title
----+-------------
  1 | Electrician
  2 | Mountaineer
  3 | Gangster
  4 | Plumber
  5 | Actor
  6 | Musician
(6 rows)
SELECT * FROM people ORDER BY id;
 id | firstname | lastname | job_id
----+-----------+----------+--------
  1 | Dave      | Smith    |      1
  2 | Tenzing   | Norgay   |      2
  3 | Anne      | Wilson   |      1
  4 | Ta        | Mok      |      3
  5 | Viv       | Richards |      4
  6 | Jane      | Campion  |      1
  7 | Shakib    | Khan     |      5
  8 | Ayub      | Bachchu  |      6
(8 rows)

Read the job_id column downwards: 1, 1, 1 for Dave, Anne and Jane. Three people now share one row in jobs, so the text Electrician is stored once and the link between the copies is explicit — it is the same number, and the database knows it.

4. Getting the original view back

You have not lost the table from section 1 — you can rebuild it any time by joining the two halves back together:

SELECT p.id, p.firstname, p.lastname, j.title AS job_title
FROM people p JOIN jobs j ON j.id = p.job_id
ORDER BY p.id;
 id | firstname | lastname |  job_title
----+-----------+----------+-------------
  1 | Dave      | Smith    | Electrician
  2 | Tenzing   | Norgay   | Mountaineer
  3 | Anne      | Wilson   | Electrician
  4 | Ta        | Mok      | Gangster
  5 | Viv       | Richards | Plumber
  6 | Jane      | Campion  | Electrician
  7 | Shakib    | Khan     | Actor
  8 | Ayub      | Bachchu  | Musician
(8 rows)

Identical to the single table, row for row. JOIN ... ON j.id = p.job_id is the instruction "for each person, go and fetch the job row they point at".

Identical is a claim, so let us check it properly. EXCEPT returns rows in the first query that are missing from the second, so running it both ways proves the two versions hold exactly the same information: 

SELECT count(*) AS rows_only_in_flat FROM (
    (SELECT firstname, lastname, job_title FROM people_flat)
    EXCEPT
    (SELECT p.firstname, p.lastname, j.title
     FROM people p JOIN jobs j ON j.id = p.job_id)
) AS diff;
 rows_only_in_flat
-------------------
                 0
(1 row)
SELECT count(*) AS rows_only_in_join FROM (
    (SELECT p.firstname, p.lastname, j.title
     FROM people p JOIN jobs j ON j.id = p.job_id)
    EXCEPT
    (SELECT firstname, lastname, job_title FROM people_flat)
) AS diff;
 rows_only_in_join
-------------------
                 0
(1 row)

Zero rows lost, zero rows invented. The split is lossless — and what you paid for it is that every question about people and their jobs now needs a JOIN. That is the trade, and it is usually worth it.

5. What the database now enforces for you

Three things become impossible, or at least loud, once the foreign key and the UNIQUE are in place.

A person cannot be given a job that does not exist

INSERT INTO people (firstname, lastname, job_id)
VALUES ('Test', 'Person', 99);
ERROR:  insert or update on table "people" violates foreign key constraint "people_job_id_fkey"
DETAIL:  Key (job_id)=(99) is not present in table "jobs".

A job cannot be deleted while people still do it

DELETE FROM jobs WHERE id = 1;
ERROR:  update or delete on table "jobs" violates foreign key constraint "people_job_id_fkey" on table "people"
DETAIL:  Key (id)=(1) is still referenced from table "people".

Anomaly 2 is now a refusal rather than a silent loss. You cannot delete Musician by deleting Ayub, because Ayub is not where the job lives.

The same title cannot be stored twice

INSERT INTO jobs (title) VALUES ('Plumber');
ERROR:  duplicate key value violates unique constraint "jobs_title_key"
DETAIL:  Key (title)=(Plumber) already exists.

And the change from anomaly 1, done properly — one fact, one row:

BEGIN;
UPDATE jobs SET title = 'Electrical Technician' WHERE id = 1;
SELECT count(*) AS rows_changed FROM jobs WHERE title = 'Electrical Technician';
ROLLBACK;
BEGIN
UPDATE 1
 rows_changed
--------------
            1
(1 row)

ROLLBACK

UPDATE 3 became UPDATE 1. That difference is the whole point of the exercise.

Be honest about what the split does not fix. A misspelling is not a duplicate, so UNIQUE will not stop it: 

BEGIN;
INSERT INTO jobs (title) VALUES ('Electrican');
SELECT count(*) AS jobs_now FROM jobs;
SELECT count(*) AS people_still FROM people;
ROLLBACK;
BEGIN
INSERT 0 1
 jobs_now
----------
        7
(1 row)

 people_still
--------------
            8
(1 row)

ROLLBACK

It went in without complaint. The database cannot know your Electrican was meant to be Electrician — to Postgres those are two different strings, and it will happily keep both.

What the split does give you is a place to notice. There are now six job rows in one small table, so a stray seventh stands out immediately — and fixing it is one UPDATE on one row, with the foreign key guaranteeing the people who pointed at it follow along. In the flat table the same typo was invisible: one row out of eight, in a column of free text, quietly claiming a job nobody else has.

6. Your turn

Three questions. The expected row counts are given so you can tell whether you are right without asking me.

Which job titles are held by more than one person?

Expected: 1 row, columns job_title, people. Use the flat table — this is the question that motivates everything above.

Answer 
SELECT job_title, count(*) AS people FROM people_flat
GROUP BY job_title HAVING count(*) > 1;
  job_title  | people
-------------+--------
 Electrician |      3
(1 row)

HAVING, not WHERE: the condition is about a group (count(*)), and WHERE runs before the groups exist.

List every person with their job title, from the two split tables

Expected: 8 rows, columns firstname, lastname, title, in people.id order.

Answer 
SELECT p.firstname, p.lastname, j.title
FROM people p JOIN jobs j ON j.id = p.job_id
ORDER BY p.id;

The output is the eight-row table printed in section 4 — same rows, same order. If you got 48 rows, you wrote FROM people, jobs without the ON: that is every person matched with every job, which is not what JOIN means.

Add a job called Blacksmith that nobody does yet

Expected: INSERT 0 1, then 7 jobs and 8 people. This is anomaly 3, fixed.

Answer 
INSERT INTO jobs (title) VALUES ('Blacksmith');

SELECT count(*) AS jobs  FROM jobs;
SELECT count(*) AS people FROM people;
INSERT 0 1
 jobs
------
    7
(1 row)

 people
--------
      8
(1 row)

One new job row, and not a single person added — the fact now has somewhere to live on its own. Note this changes your table: from here on there are 7 jobs, not 6. If you want the starting state back, re-run psql -U postgres -f second_normal.sql.

7. So is this second normal form?

The page is called second_normal, so this deserves a straight answer: the table in section 1 is already in second normal form, and in third normal form as well. The rule for 2NF is that every non-key column must depend on the whole key, not on part of it — and a rule about parts of a key only has teeth when the key has more than one column.

Our key is id (or firstname, lastname if you prefer the natural key). Both are single facts about a person, and job_title needs the whole person to be determined. No column depends on a fragment of the key, so there is nothing for 2NF to object to. Splitting jobs out is what people usually call extracting a lookup table, and it is justified by the anomalies in section 2, not by a normal-form violation.

A real 2NF violation needs a composite key and a column that only needs part of it. The classic shape is a table recording who works which job, where the rate belongs to the job rather than to the pairing:

CREATE TABLE work (
    person_id integer REFERENCES people(id),
    job_id    integer REFERENCES jobs(id),
    rate      numeric(6,2) NOT NULL,
    PRIMARY KEY (person_id, job_id)
);

You do not need to run this — it is here to show the shape. The key is (person_id, job_id), and rate is determined by job_id alone: change the job and the rate is fixed, whoever is doing it. A column that depends on part of the key is exactly what 2NF forbids. The fix is to move rate into jobs and leave work holding nothing but the two ids — and that fix needs three tables, not two.

One sentence to take away. The two-table split is the fix you will actually reach for; 2NF is the rule that describes a narrower case of the same idea — every column should depend on the whole key, and on nothing else.

What you just did. You built one table, watched a single fact get stored three times, saw three anomalies fall out of that, split the table in two with a foreign key, proved with EXCEPT that nothing was lost, and saw three constraints start refusing bad data on your behalf.

The next thing to try is a third table: if a person can hold more than one job, the job_id column in people has to go, and the link between people and jobs becomes a table of its own — which is precisely the work table sketched above.
