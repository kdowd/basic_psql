Lesson
45–60 minutes

Create a database, a table, and read it back

Objectives · single topic · 45–60 minutes

You will build a small database from scratch inside a psql session, put a table in it, fill the table with eight rows, and read them back. Nothing is simulated: every command and every line of output on this page came from the PostgreSQL 18.6 server running on this machine, so when your screen matches, you are right.

Never used a database before? Open basic_usage.html first. It is the same five commands in six short steps, with no jargon. This page is the one to come back to afterwards.

Assumptions. You have never created a database before. psql is installed and a server is already running on localhost:5432. You can connect as the postgres role. You have 45–60 minutes. No other dataset is needed.

By the end you will be able to

  1. Connect to the running server with psql, and prove which database and which user you are talking to.
  2. Create a database called blah_db and a table users whose four columns have types you chose yourself.
  3. Insert eight rows in one statement, including a name that contains an apostrophe.
  4. Read the rows back with a SELECT, and state the row count and column list of any query you write before you run it.
  5. Predict what a missing value does to count(), to a comparison, and to a sort — before you run the query.

What you are building

server   localhost:5432   (PostgreSQL 18.6, already running)
└── database  blah_db          <- you create this
    └── table  public.users       <- you create this
        ├── firstname   text
        ├── lastname    text
        ├── age         integer
        └── email       text
            └── 8 rows            <- you insert these

How to use this page

  • Read Build it once without typing, then do it again with psql open beside it.

  • Keep two numbers in your head the whole way through: 8 (the rows you inserted) and 7 (the rows that actually have an age). Every trap in this lesson lives in the gap between them.

Setup

Step 0 · about five minutes

The server is already running, so setup is only about getting into it and checking where you landed.

  1. Start psql as the postgres role

    psql -U postgres

    -U postgres is the default user. So you are logging in as a database superuser.

  2. Read the prompt

    Your prompt changes to postgres=#. That single line tells you two things: the word before = is the database you are connected to, and a # at the end means you are a superuser. An ordinary user gets > instead.

  3. List the databases that already exist

    \l

    Lines starting with a backslash are not SQL — they are psql meta-commands, handled by the client. \l asks the server for its database list:

                                                      List of databases
     Name      |  Owner   | Encoding | Locale Provider | Collate | Ctype | Locale
---------------+----------+----------+-----------------+---------+-------+--------
 blahworld     | postgres | UTF8     | libc            | C       | C     |
 my_special_db | postgres | UTF8     | libc            | C       | C     |
 postgres      | postgres | UTF8     | libc            | C       | C     |
 template0     | postgres | UTF8     | libc            | C       | C     |
 template1     | postgres | UTF8     | libc            | C       | C     |
(5 rows)

    Your list will differ — mine happens to hold two leftovers from earlier experiments. Two names are always there: postgres, the maintenance database you are sitting in now, and the two template databases that new databases are copied from. The privileges column is trimmed here for width.

  4. Confirm the environment works

    Ask the server to identify itself, and run it as the skill's environment check. If you get one row back, everything below will work.

    SELECT current_database(), current_user, version();
     current_database | current_user |                                 version
------------------+--------------+-------------------------------------------------------------------------
 postgres         | postgres     | PostgreSQL 18.6 on x86_64-windows, compiled by msvc-19.44.35228, 64-bit
(1 row)

    Expected: 1 row, 3 columns. Note you are in the database postgres — that is about to change.

Meta-commands you will use

These are typed at the psql prompt like commands, not terminated with a semicolon:

Commands are prefixed with a backslash (\) and are not SQL statements. DO NOT use semicolons after them.

Command What it does
\l List every database on the server.
\c blah_db Connect to a different database without leaving psql.
\dt List the tables in the database you are connected to.
\d users Describe one table: its columns, their types, and what is nullable.
\conninfo Print which database, user, host and port this session is using.
\q Quit psql.

Faster path, once you have read Build it. The whole lesson is also saved as one script in this folder: 

psql -U postgres -f blah_db.sql

It is the same commands in the same order. Read the next tab first — the script is for re-running, not for learning from. Re-running is safe: it drops and rebuilds the users table, so you always finish at exactly eight rows. Expect one red line on a second run: 

ERROR:  database "blah_db" already exists

That is the CREATE DATABASE line noticing the work is already done. psql keeps going and everything after it succeeds. The only path that is not safe is running the INSERT repeatedly without the drop — that is how you get sixteen rows and a lesson whose every expected count is wrong.

Build it

Worked example · eight statements · every output below is real

This is the whole job, in the order I ran it. Type along; the output you get back should match what is printed under each command.

  1. Create the database

    CREATE DATABASE blah_db;
    CREATE DATABASE

    Why: a database is the container everything else lives inside. You are currently sitting in postgres, the maintenance database the server keeps for itself, and putting your practice tables there is like storing your notes in Windows' System32. CREATE DATABASE makes a fresh, empty one. The reply is a command tag — the server repeating back what it did, not a result set.

  2. Move into it

    \c blah_db
    You are now connected to database "blah_db" as user "postgres".

    Why: creating a database does not enter it. \c reconnects the current session, and from here on every statement lands in blah_db. Confirm it two ways: the prompt is now blah_db=#, and \conninfo agrees.

  3. Create the table

    CREATE TABLE users (
    firstname text,
    lastname  text,
    age       integer,
    email     text
);
    CREATE TABLE

    Why: a table is a named list of columns, and every column must declare a type before it can hold anything. The names are yours to choose; the types are the database's business, and they are what stop an age from being the word thirty. Two details worth noticing: statements end with a semicolon, and the line breaks and indentation are only for humans — the server sees one statement either way.

  4. Check what the database actually stored

    \d users
                     Table "public.users"
  Column   |  Type   | Collation | Nullable | Default
-----------+---------+-----------+----------+---------
 firstname | text    |           |          |
 lastname  | text    |           |          |
 age       | integer |           |          | 
 email     | text    |           |          |

    Why: \d reads the table back out of the database, so it shows you what was really created rather than what you meant to create. Note public.users: Postgres put your table in a schema called public, and Nullable is blank for all four columns, meaning every one of them will accept a missing value. That is a decision you made by not making one, and exercise 2 is where it bites.

  5. Insert the rows

    INSERT INTO users (firstname, lastname, age, email) VALUES
    ('Mary',  'Johnson', 34,   'mary.johnson@example.com'),
    ('James', 'Smith',   41,   'james.smith@example.com'),
    ('Aroha', 'Ngata',   29,   'aroha.ngata@example.com'),
    ('Liam',  'O''Brien', 52,  'liam.obrien@example.com'),
    ('Priya', 'Sharma',  NULL, 'priya.sharma@example.com'),
    ('Tomas', 'Novak',   45,   NULL),
    ('Mary',  'Johnson', 34,   'Mary.Johnson@Example.Com'),
    ('Sofia', 'Rossi',   17,   'sofia.rossi@example.com');
    INSERT 0 8

    Why: one statement, eight rows. Read the tag INSERT 0 8 right to left: 8 is the number of rows inserted, and the 0 is a legacy object identifier that Postgres has reported since before you were born — ignore it, but never ignore the second number.

    Three things in that statement are deliberate. NULL is a keyword written without quotes, meaning no value here — Priya has no recorded age and Tomas has no email. O''Brien is how an apostrophe is escaped inside a string: two single quotes, because one would end the string early. And the two Mary Johnson rows are not a typo — duplicated people are the normal state of real data.

  6. Read it back

    SELECT firstname, lastname, age, email FROM users;
     firstname | lastname | age |          email
-----------+----------+-----+--------------------------
 Mary      | Johnson  |  34 | mary.johnson@example.com
 James     | Smith    |  41 | james.smith@example.com
 Aroha     | Ngata    |  29 | aroha.ngata@example.com
 Liam      | O'Brien  |  52 | liam.obrien@example.com
 Priya     | Sharma   |     | priya.sharma@example.com
 Tomas     | Novak    |  45 |
 Mary      | Johnson  |  34 | Mary.Johnson@Example.Com
 Sofia     | Rossi    |  17 | sofia.rossi@example.com
(8 rows)

    Why: SELECT names the columns you want and FROM names the table to take them from. The gaps in the age and email columns are the NULLs, printed as blank space rather than the word NULL — worth remembering, because a blank in the output does not always mean a blank in the data.

    One honesty note: this output came back in insertion order, but you did not ask for any order. Without ORDER BY, the server is free to return rows in any order it likes, and it will change its mind as the table grows.

Result of the worked example: 8 rows, columns firstname, lastname, age, email. If you have that, the database exists, the table exists, and the data is in it.

Try breaking it once, on purpose. The type you chose in step 3 is enforced, not decorative. Paste text into the age column and the whole statement is rejected:

INSERT INTO users (firstname, lastname, age, email)
VALUES ('Test', 'Row', 'thirty', 'test@example.com');
ERROR:  invalid input syntax for type integer: "thirty"
LINE 2: VALUES ('Test', 'Row', 'thirty', 'test@example.com');
                               ^

The row was not added — check with SELECT count(*) FROM users; and you still get 8. A failed statement is not a half-finished statement.

Practice

One guided exercise, then four problems

Every problem runs against the same users table you just built, and each one adds a single new idea to the one before it. Answers are on the Solutions tab — do not open it until you have either a row count that matches or a clear question about why it does not.

Guided exercise — fill in the gaps

Goal: show first name, last name and email for everyone aged 30 or over, youngest first. The structure is supplied; you supply the three missing pieces.

SELECT firstname, lastname, email
FROM   <which table?>
WHERE  <which rows survive?>
ORDER BY <by what, and in which direction?>;

Expected: 5 rows, 3 columns.

Hints
  1. Restate. You are keeping a subset of the rows and presenting them in a stated order — one clause decides membership, another decides sequence.
  2. Point. WHERE filters rows; ORDER BY sorts them. Ascending is the default, and "youngest first" is the direction the numbers already run in.
  3. Edge. "30 or over" is a boundary, so decide deliberately between > and >=: one of them silently drops the 34-year-olds and every other exact-thirty. There is nobody aged exactly 30 in this table, so your count is the only thing that will tell you which you picked.

Exercise 1 — who is old enough to sign?

List every user aged 18 or over, oldest first. Show firstname, lastname and email.

Expected: 6 rows, columns firstname, lastname, email.

Check your answer:

SELECT count(*) AS rows_returned, min(age) AS youngest, max(age) AS oldest
FROM users WHERE age >= 18;   -- expected: 6 | 29 | 52
Hints
  1. Restate. This is the guided exercise with a different boundary and the opposite direction — the shape of the query does not change.
  2. Point. WHERE age >= 18 chooses the rows, ORDER BY age DESC puts the largest first.
  3. Edge. Rows leave this result for two different reasons, and only one of them is "too young". A comparison against a missing value is neither true nor false, so the row with no age is not returned — and it is not returned by < 18 either. If your count is 5, look at which of the eight rows never appears in any of your results.

Exercise 2 — how old is everyone, on average?

Report two numbers in one row: how many of the eight rows actually have an age recorded, and the average of the ages you do have, rounded to one decimal place.

Expected: 1 row, 2 columns. One of them is 7.

Check your answer:

SELECT count(age) AS n, sum(age) AS total FROM users;   -- expected: 7 | 252

Your average must equal 252 / 7. If your two numbers are 7 and 252, your average is right by construction.

Hints
  1. Restate. You are collapsing eight rows into one summary row. That is a different kind of query from everything so far.
  2. Point. count() and avg() are aggregates — they take a column and return one value. count(*) counts rows; count(age) counts rows where the age is present. Those are two different questions, and this exercise wants the second one. round(value, 1) tidies the average.
  3. Edge. Your divisor is 7, not 8. If your average comes out as 31.5, you divided by 8 — you counted a row that contributes nothing to the sum. A missing value is skipped by avg(), not treated as zero.

Exercise 3 — the same person, twice

One person appears in the table more than once. Write a query that returns each first-name/last-name pair that occurs more than once, together with the number of times it occurs. No structure given this time.

Expected: 1 row, 3 columns.

Check your answer:

SELECT count(*) AS distinct_people
FROM (SELECT DISTINCT firstname, lastname FROM users) AS people;   -- expected: 7

Eight rows describe seven distinct people, so exactly one name repeats.

Hints
  1. Restate. You want one output row per person rather than one per input row — a summary computed per group.
  2. Point. GROUP BY firstname, lastname defines what "the same person" means; with groups in place, count(*) counts the rows inside each one.
  3. Edge. Filtering the groups is a different clause from filtering the rows: WHERE runs before grouping and cannot see count(*). If your output lists all seven people, you filtered at the wrong level.

Exercise 4 — Mary, without guessing her capitals

One email address in the table was typed with capital letters. Write a query that finds every row whose email address is mary.johnson@example.com, regardless of how it was capitalised. Show firstname and email.

Expected: 2 rows, columns firstname, email.

Check your answer:

SELECT email FROM users WHERE email <> lower(email);   -- expected: 1 row

That single row is the odd one out. If your exercise query returned only one row, you compared against the raw column and it did not match.

Hints
  1. Restate. This is exercise 1's filter with one change: equality has to stop caring about case.
  2. Point. The = operator compares text exactly, character by character. Either normalise both sides (lower(email) = lower('...')) or use the case-insensitive operator ILIKE.
  3. Edge. Only one of the two rows is already lowercase, so a query that returns one row has compared the stored value rather than a normalised one. Nothing is wrong with your quotation marks — the two addresses really are different strings to the database.

Solutions

Runnable as written · output shown is what the server returned

Guided exercise

SELECT firstname, lastname, email
FROM users
WHERE age >= 30
ORDER BY age;
 firstname | lastname |          email
-----------+----------+--------------------------
 Mary      | Johnson  | mary.johnson@example.com
 Mary      | Johnson  | Mary.Johnson@Example.Com
 James     | Smith    | james.smith@example.com
 Tomas     | Novak    |
 Liam      | O'Brien  | liam.obrien@example.com
(5 rows)

Five rows, and the two Marys sit next to each other because they share an age — their relative order is not something the query promised. Note the blank email on Tomas: the row is still a row.

Exercise 1 — 18 or over, oldest first

SELECT firstname, lastname, email
FROM users
WHERE age >= 18
ORDER BY age DESC;
 firstname | lastname |          email
-----------+----------+--------------------------
 Liam      | O'Brien  | liam.obrien@example.com
 Tomas     | Novak    |
 James     | Smith    | james.smith@example.com
 Mary      | Johnson  | mary.johnson@example.com
 Mary      | Johnson  | Mary.Johnson@Example.Com
 Aroha     | Ngata    | aroha.ngata@example.com
(6 rows)

Six rows, not seven: Sofia is 17, and Priya is neither 18 nor younger. The near-miss to avoid is writing WHERE age > 18, which drops nobody in this particular table — check the count and you cannot tell you were wrong. That is exactly why the exercise gives you the expected count.

Exercise 2 — count and average

SELECT count(age) AS with_age, round(avg(age), 1) AS average_age
FROM users;
 with_age | average_age
----------+-------------
        7 |        36.0
(1 row)

count(age) skips the missing value; avg(age) skips it too, and divides by 7, not 8. The near-miss is count(*) in the numerator or the denominator: 252 / 8 is 31.5, an answer that looks entirely plausible and is wrong.

Exercise 3 — repeated people

SELECT firstname, lastname, count(*) AS copies
FROM users
GROUP BY firstname, lastname
HAVING count(*) > 1;
 firstname | lastname | copies
-----------+----------+--------
 Mary      | Johnson  |      2
(1 row)

The near-miss is filtering with WHERE count(*) > 1, which errors because WHERE runs before the groups exist. Groups are filtered by HAVING, and the clause order in the statement is not the order the server executes it in.

Exercise 4 — case-insensitive match

SELECT firstname, email
FROM users
WHERE lower(email) = 'mary.johnson@example.com';
 firstname |          email
-----------+--------------------------
 Mary      | mary.johnson@example.com
 Mary      | Mary.Johnson@Example.Com
(2 rows)

The equivalent with the other tool:

SELECT firstname, email FROM users WHERE email ILIKE 'mary.johnson@example.com';

The near-miss is WHERE email = 'mary.johnson@example.com', which returns one row and looks correct until you remember there are two Marys. Note that ILIKE also treats % and _ as wildcards, so lower() on both sides is the safer habit for exact matching.

Self-check

  • \dt lists one table, users, and \d users shows four columns of types text, text, integer, text.
  • SELECT count(*) FROM users; returns 8.
  • SELECT count(age) FROM users; returns 7.
  • Your exercise 2 average is 36.0.
  • Your exercise 3 output names exactly one repeated person.
  • Your exercise 4 output returns 2 rows.

Traps

Three wrong mental models this topic reliably produces

"A missing value is just an empty one — I can compare with it."

Why it is tempting: a blank cell looks like a blank string, and every other value in the table behaves like a value. So you expect age <> 40 to return the seven rows that are not 40.

What actually happens: NULL means unknown. Any comparison with it returns unknown, and unknown is not true, so the row is filtered out.

SELECT count(*) AS rows_total, count(age) AS rows_with_age FROM users;
 rows_total | rows_with_age
------------+---------------
          8 |             7
(1 row)
SELECT firstname, lastname, age FROM users WHERE age <> 40 ORDER BY age;
 firstname | lastname | age
-----------+----------+-----
 Sofia     | Rossi    |  17
 Aroha     | Ngata    |  29
 Mary      | Johnson  |  34
 Mary      | Johnson  |  34
 James     | Smith    |  41
 Tomas     | Novak    |  45
 Liam      | O'Brien  |  52
(7 rows)

Seven rows — but from a table of eight, and Priya's age is not 40, so she should be there. The filter removed her without saying so. The same misunderstanding shows up in sorting, where the word "unknown" has to be placed somewhere: 

SELECT firstname, age FROM users ORDER BY age DESC LIMIT 3;
 firstname | age
-----------+-----
 Priya     |
 Liam      |  52
 Tomas     |  45
(3 rows)

Postgres sorts NULL as if it were larger than every real value, so "highest first" opens with a blank. Write ORDER BY age DESC NULLS LAST when you care.

"Text comparison ignores capitalisation."

Why it is tempting: email addresses, file names and web addresses are case-insensitive almost everywhere else you meet them, so two addresses that differ only in case feel like the same address.

What actually happens: Postgres compares text exactly. These two queries differ by one function and by one row:

SELECT firstname, email FROM users WHERE email = 'mary.johnson@example.com';
 firstname |          email
-----------+--------------------------
 Mary      | mary.johnson@example.com
(1 row)
SELECT firstname, email FROM users WHERE lower(email) = 'mary.johnson@example.com';
 firstname |          email
-----------+--------------------------
 Mary      | mary.johnson@example.com
 Mary      | Mary.Johnson@Example.Com
(2 rows)

If your data has this problem at scale, the fix is a normalising constraint or a case-insensitive index — not a lower() wrapped around every query forever. For now, the lesson is simply that = means exactly.

"A table name is whatever I typed."

Why it is tempting: you wrote CREATE TABLE users, and elsewhere you have seen people write Users. Surely the database keeps the capital letter.

What actually happens: an unquoted identifier is folded to lower case before it is stored. So Users and users are the same table, and the only way to get a capital letter into a name is to quote it — after which it is a different name, and a strict one: 

SELECT count(*) AS unquoted_works FROM Users;
 unquoted_works
----------------
              8
(1 row)
SELECT count(*) AS quoted_fails FROM "Users";
ERROR:  relation "Users" does not exist
LINE 1: SELECT count(*) AS quoted_fails FROM "Users";

The practical rule: write identifiers in lower case with underscores, never quote them, and you will never have to remember this. \dt is the tie-breaker whenever you are unsure what a table is really called.

Transfer

Same structure, different story · no new syntax

Nothing below needs a clause you have not already used. That is the point: the surface story changes, the structure does not.

A small library

Create a table books in the same blah_db database, with the same four-column shape as users:

  • title — text
  • author — text
  • year — integer
  • isbn — text

Insert six books of your own choosing, and make your data carry the same three awkwardnesses the users table carried:

  • one book with no year recorded,
  • one book with no isbn,
  • one title that appears twice (a reprint, say — same title and author).

Then answer four questions with four queries:

  1. Every book published in 1990 or later, newest first, showing title, author and year.
  2. How many books have a year recorded, and the average of those years.
  3. Which title-and-author pairs appear more than once, and how many times each.
  4. The book whose isbn is missing — the one whose ISBN you cannot look up.

Check yourself the same way: before running anything, write down the row count you expect from each query and the number of columns. For question 1 over six books with one missing year, "books from 1990 on" cannot return a count you cannot predict from your own six rows.

Hints
  1. Restate. Questions 1 and 4 are filters, question 2 is an aggregate, question 3 is a grouped aggregate — the same four shapes you have already written once.
  2. Point. Only the names changed: year takes the role age played, isbn takes the role email played.
  3. Edge. Question 4 is the one that looks new and is not: "missing" is never tested with =. Equality against a missing value is unknown, so a filter for the absent ISBN needs the operator designed for it — IS NULL.

If that felt easy, that is the real result

You created a database, created a typed table, inserted rows with an escaped quote, and queried them four different ways. The next rung — giving the table a primary key, updating a row, and deleting one — reuses every one of these clauses, so it is a short step from here rather than a new subject.

psql cheatsheet

Common commands to memorize::

Commands starting with a backslash are meta-commands: psql itself handles them, so they take no semicolon and are not case-sensitive. Everything else is SQL, and SQL is not executed until you end it with ;.

Command What it does

\conninfo Print the database, user, host and port of the session you are in.

The SQL you have already used

Statement What it does
CREATE DATABASE blah_db; Make an empty database to work inside.
CREATE TABLE users (firstname text, lastname text, age integer, email text); Make a table; every column declares its type.
INSERT INTO users (...) VALUES (...), (...); Add rows. '' escapes a quote inside a string; NULL means no value here.
SELECT firstname, age FROM users; Choose columns from a table.
WHERE age >= 18 Keep only the rows the condition is true for. Rows it cannot decide about are dropped.
ORDER BY age DESC Sort. NULL sorts as if it were larger than every real value.
LIMIT 3 Return at most three rows.
count(*) / count(age) Count rows / count rows where the age is present. 8 versus 7.
avg(age) / round(x, 1) Average the values that exist, and round the answer.
GROUP BY firstname, lastname HAVING count(*) > 1 One output row per group, then filter the groups.
age IS NULL / age IS NOT NULL Test for a missing value. Never with =.
Case insensitive search:lower(email) OR WHERE email ILIKE '%@yahoo.com' Compare text without caring about capitals.
